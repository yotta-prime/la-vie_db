# la-vie: design review and top ten improvements

October 2026, after v1 plus the O'Reilly work (schema v3, commit `0babe52`). Scope: the stack, its design, how it compares with similar projects, and what to do next.

## 1. What la-vie is, in one paragraph

A single Python container on a Synology DS220+ that **pushes** rule-based prompts to one person through Telegram across four areas (movement, focus, learning, hobbies), logs the answers, and reports weekly. Content and settings are edited in a LAN admin page or as YAML in the repo. The NAS deploys itself by pulling `main` from a public GitHub repo every 15 minutes.

## 2. Architecture as built

| Layer | Choice | Assessment |
|---|---|---|
| Runtime | FastAPI + python-telegram-bot + APScheduler in **one process** | Right size for one user. Shared in-process state is simple; the cost is that a crash or deploy takes everything down together (mitigated by Docker restart and the watchdog). |
| Messaging | Telegram **long polling**, owner chat ID only | Strong choice: no inbound ports, works behind NAT, free push notifications and buttons. |
| Storage | SQLite (WAL) on a NAS volume, nightly online backup | Ideal for one user. Hand-written migrations with a pre-migration copy are working well (v1 to v3 so far). |
| Scheduling | Prompts are **rows in the database**, planned daily and dispatched each minute | Robust: restarts don't lose the plan, and quiet hours/pauses/expiry are applied at send time. Event confirmations wait out quiet hours rather than being dropped. |
| Content | Admin forms plus `content/*.yaml` imported **add-only by key** | Good balance: files are versioned, admin edits always win, links fill in later. |
| Admin UI | Server-rendered Jinja, password and signed SameSite cookie, LAN only | Appropriate. No JavaScript build, works on a phone. |
| Deploy | DSM Task Scheduler runs `update.sh` (git pull and `docker compose up --build`) as root | Simple and transparent, but builds on the NAS, rebuilds and restarts on **every** commit (docs included), and runs whatever is on `main` with no test gate. |
| Ops | `/health` with version and polling age, watchdog restart, optional heartbeat, Docker health check | Good for a home service once the heartbeat is configured. Deploy failures are still **silent**. |
| Tests | 63 pytest tests: engine, selection, admin, migrations, content, Telegram views | Good coverage of the logic. They run only on a laptop, and the bot tests currently depend on the local `.env`. |

**Design strengths worth keeping:** push, not pull; prompts persisted as data; rules instead of AI for the daily loop (predictable, free, private); secrets outside the repo; a hardened container (non-root, read-only, no capabilities); add-only content import; and independent verification via `/health`.

## 3. Comparison with similar projects

| Project | Type | What it does better | What la-vie does that it doesn't |
|---|---|---|---|
| [Habitica](https://habitica.com) | Hosted, gamified habits | Motivation mechanics, mobile apps, social features | Self-hosted, private, proactive scheduled nudges, learning paths |
| [Loop Habit Tracker](https://github.com/iSoron/uhabits) | Android, offline | Excellent charts: habit strength, calendar heatmaps, history | Multi-domain plans, courses, events, two-way Telegram |
| [Beaver Habits](https://github.com/daya0576/beaverhabits), [HabitTrove](https://railway.com/deploy/habittrove-template.md), [MyDailies](https://pkg.go.dev/github.com/FR0ST1N/MyDailies) | Self-hosted web habit trackers | Visual progress, one-tap check-ins in a web or PWA UI | Prompts *come to you*; scheduling rules; unlocks |
| [OpenMemo](https://github.com/haerincode/openmemo), [TG-Reminder](https://beta.pkg.go.dev/github.com/mezk/tg-reminder) | Self-hosted Telegram bots | Free-form capture ("second brain"), ad-hoc reminders | Structured areas, weekly report, learning model |
| [Anki](https://apps.ankiweb.net) / [FSRS ecosystem](https://github.com/open-spaced-repetition/awesome-fsrs), Obsidian or Logseq SR plugins | Spaced repetition | Mature FSRS scheduling, huge card ecosystem | Course/lesson/event lifecycle around the cards |
| n8n, Huginn, Home Assistant automations | General automation | Email to Telegram flows without code, many connectors | A coherent domain model and history; tests |

**Where la-vie sits:** most self-hosted trackers are *passive* (you open them and tick things). la-vie is *proactive*: it plans the day and asks. That's its distinctive value, and it's also where it's weakest relative to the field: it has **no visual progress**, and its only "UI" for daily use is chat. The learning side (paths, courses, events with attendance and recordings, unlocks) has no close equivalent among small self-hosted tools.

On deployment, the common patterns for Synology are a git-pull cron like ours, Watchtower for image updates, webhook containers with the Docker socket, or CI-built images. Watchtower only updates images, not compose or config changes ([discussion](https://lemmy.klein.ruhr/post/491/4556), [Synology guide](https://drfrankenstein.co.uk/watchtower-automated-updates-in-container-manager-on-a-synology-nas/)). The usual next step from a git-pull cron is **build in CI, pull an image on the NAS**.

## 4. Risks found

1. **Untested commits go live.** Anything on `main` is deployed within 15 minutes, root-run, with no test gate. A broken import would take the bot down until someone notices.
2. **Unreproducible builds.** `requirements.txt` uses `>=` ranges and the base image is `python:3.12-slim` (its digest changed between two builds on 4 October). Every rebuild can pull new library versions; a breaking release would surface as a failed deploy on the NAS.
3. **Silent deploy failures.** `update.sh` logs to a root-only file; nothing tells you a deploy failed.
4. **Backups on the same disk.** Nightly copies live on the NAS volume; Hyper Backup isn't configured yet and a restore has never been tested.
5. **Every commit restarts the bot,** including docs-only ones (the version build argument changes the image).
6. **The public repo carries operational detail:** the chat history, the NAS address and username, and the deploy layout. That's harmless on its own (nothing is reachable from the internet) but it adds up. The O'Reilly links were a deliberate choice and aren't counted here.
7. **Small in-memory state:** `/log` area questions and the Telegram polling clock are lost on restart (minor).
8. **Test isolation:** bot tests read the developer's `.env` (currently 5 failures locally without an override).

## 5. Top ten improvements (ranked by value for effort)

| # | Improvement | Why | Effort |
|---|---|---|---|
| 1 | **CI on GitHub: run the tests on every push; the NAS deploys only commits that passed.** `update.sh` checks the commit's status via the GitHub API before pulling. Also isolate the tests from `.env`. | Closes risk 1, the biggest one; makes "push to main" safe. | S |
| 2 | **Reproducible builds:** lock dependencies (`pip-compile` / `uv lock`), pin the base image by digest, and let Dependabot propose updates as pull requests that CI tests. | Removes surprise breakages on the NAS (risk 2). | S |
| 3 | **Deploy alerts:** if `update.sh` fails, send a Telegram message via the Bot API (token already on the NAS); also configure the healthchecks.io heartbeat that's already built. | You hear about failures within minutes, not days (risk 3, and Friday's silent outage). | S |
| 4 | **Off-NAS backups and a restore drill:** Hyper Backup of `data/backups` to Synology C2 or a USB disk; keep the `.env` values in your password manager; test a restore into a scratch container once. | Data is the only irreplaceable part (risk 4). | S |
| 5 | **Build images in CI (GHCR), and have the NAS pull an image tag instead of building.** Skip deploys when only docs changed. | Faster, identical builds; instant rollback by tag; no restarts for docs (risk 5). Pairs with #1 and #2. | M |
| 6 | **Progress page:** calendar heatmaps per area, course and path progress bars, and an O'Reilly watch-backlog burndown on the admin site, with a weekly chart image in the Sunday summary. | The main gap against Loop, Beaver and Habitica: seeing progress is itself motivating. | M |
| 7 | **Close the learning loop:** after "✓ Watched", ask for 1–3 takeaways (a reply); store them on the lesson; turn chosen ones into FSRS flashcards (`py-fsrs`), finishing the planned flashcard feature. | Turns watching into retention; uses the FSRS choice from the spec. | M |
| 8 | **Calendar feed (ICS):** a private subscription URL with upcoming O'Reilly events and planned learning/hobby sessions, for your phone calendar. | Events and sessions appear where you plan your day; cheap to build from existing data. | S |
| 9 | **Adaptive nudges:** track answer rate and delay per prompt type and time; the weekly summary suggests changes (e.g. "hobby prompts at 19:00 are answered 30% of the time; try 20:00?"), applied from a button. | Fewer ignored prompts; keeps rules-based behaviour, explained. | M |
| 10 | **Tighten the trust boundary:** make the repo private with a read-only deploy key (or deploy only signed release tags), and move chat histories out of the public repo. | GitHub access is effectively root on the NAS; the less public operational detail, the better (risk 6). | S |

**Honourable mentions:** remote admin access via Tailscale (already parked); persist the `/log` pending state in the database; `/undo` for the last log; per-area quiet hours; a PWA shortcut for the admin page; and an optional AI layer kept separate from the daily loop (Radar summaries and weekly reflections), with a monthly cost cap.
